## 1. アーキテクチャ & パフォーマンス

### エドオク: 積み上げ型 WordPress
WordPress に独自プラグインを重ねた構成。立ち上げは速いが、テーマとプラグインが密結合し、
PHP と WordPress 本体の制約を受ける。ページ遷移のたびに画面全体を読み直すため、
入札のたびに一瞬の待ちが発生する。

### 播州オク: 設計済み Next.js
React Server Components とサーバーアクションで、サーバー描画の速さと、
画面を再読込しない滑らかな部分更新を両立。依存は `next` / `react` / `nodemailer` / `sharp` と
組込 SQLite のみで軽量。マイページのタブ切替も入札も画面が白く点滅しない。

**播州オクの優位**
- 再読込ゼロの操作感（ネイティブアプリに近い）
- 最小依存で改修が速く、障害点が少ない
- TypeScript 型安全 ＋ 44件の自動テストで回帰を防止
- PWA でスマホのホーム画面に常駐できる

**今後の論点**
- データベースは現在 SQLite 単機（`src/lib/db.ts`）。会員・同時接続が増えたら PostgreSQL 等への移行設計が必要
- 画像・バックアップを含むインフラ運用の整備（`data/` ボリューム）

> 結論: 描画速度・操作感・保守性は播州オクが明確に優位。拡大期のDB／インフラ設計が次の宿題。

## 2. スマホ入札 UX・デザイン

エドオクは PC 向けレイアウトを踏襲し、スマホでは縦長スクロール中心。
播州オクはスマホでの入札を最優先に設計している（水鏡シアン体系）。

- **StickyBidBar（下部固定バー / `src/components/StickyBidBar.tsx`）**: どこまでスクロールしても
  画面最下部に入札導線が固定され、「入札したい瞬間」を逃さず離脱を防ぐ。
- **クイック入札チップ（`src/components/BidBox.tsx`）**: ＋100／＋500／＋1,000円をワンタップで加算。
  指での打ち間違いを防ぎ、競りのテンポを生む。
- **上限額の自動代理入札 ＋ 確認画面**、**1:1正方形ギャラリー＋遊泳動画枠（`src/components/Gallery.tsx`）**、
  **入札者名をマスクしたライブ履歴（`src/components/LiveBoard.tsx`）**。

> この片手操作の完成度が、現時点での最大の体感的アドバンテージ。

## 3. 信頼・血統証明のギャップ

**誤解されやすい点**: 播州オクは**すでに起点販売証明（sale）と二次販売・系統継承証明（secondary）の
2重台帳**を実装済み（`src/lib/certificates.ts`）。親子関係をたどる系統チェーン（`lineage()`）と、
**公開照合ページ（有効／無効をリアルタイム表示 / `src/app/certificates/[code]/page.tsx`）**も動いている。
基礎はエドオクと同じ土俵。差がつくのは「現物とつなぐ導線」と「可視化」。

**実装済み**
- 起点（sale）＋二次（secondary）の2重台帳（`parent_id` で系統を連結）
- 証明書番号による公開照合ページ、有効／確認待ち／無効のステータス表示

**埋めるべきギャップ**
- **QRコード未発行**: 現物から照合ページへ飛べない（エドオクはQR同梱）
- **家系図が縦一列**: `lineage()` は直線チェーン。最大6世代の分岐ツリーとして見せたい
- **EXIF/GPS自動削除**: 本PRで実装済み（下記 4 を参照）。盗難・養魚場特定リスクへの対応

## 4. 画像セキュリティ・最適化パイプライン（本PRで実装）

メダカの出品写真には、スマホの EXIF に撮影場所の GPS 座標・撮影日時・端末名が埋め込まれていることが多い。
これをそのまま公開すると養魚場の特定や盗難につながる。本PRで保存前の無害化・最適化を実装した。

### 実装
- `src/lib/image-pipeline.ts` — `processUploadImage()`
  1. **EXIF / GPS / 撮影日時 / 端末名を完全除去**（`sharp` は出力時に明示しない限りメタデータを引き継がない。
     `rotate()` で向きだけ画素に焼き込んでからメタデータごと破棄）
  2. **WebP へ変換・最適化**（`quality: 80`）
  3. **長辺を最大 1600px にリサイズ**（拡大はしない・比率維持）
- `src/lib/uploads.ts` — `saveImage()` がこのパイプラインを経由。保存されるのは常に `.webp`。
  出品フォーム（`src/app/sell/actions.ts`）の画像アップロードに自動適用される。

### テスト（`tests/image-pipeline.test.ts`）
- GPS/EXIF（端末名含む）を埋め込んだ JPEG を入力し、**処理後に位置情報・EXIFが完全消去**されること
- **WebP 形式で出力**され、長辺 1600px にリサイズされること
- 小さい画像は拡大されないこと

> 実測例: 2400×1800 の GPS 付き JPEG（約26KB）→ 1600×1200 の WebP（約3.5KB）、EXIF 完全消去。

## 5. リアルタイム性 & 通知設計

### 通知: すでに到達済み
播州オクは **LINE Messaging API のプッシュ通知とメールの二重配信**（`src/lib/notify.ts`）、
および **LINEログイン**（`src/lib/line-login.ts`）を実装済み。エドオクの LINE エコシステムには
機能として到達している。残りは通知テンプレの充実（高値更新／終了10分前／落札）と配信信頼性。

### リアルタイム: ここが本丸
画面更新は現状 3秒ごとのポーリング（`src/components/LiveBoard.tsx` → `/api/listings/[id]/live`）。
多人数が同時に競る終了間際に遅延とサーバー負荷が出る。

**推奨ロードマップ**
- **Phase 1 — SSE（Server-Sent Events）**: 価格と履歴をサーバーから押し出す。追加依存が少なく自前で組める第一歩。反映を1秒未満へ。
- **Phase 2 — Supabase Realtime もしくは専用 WebSocket（Pusher/Ably）**: 入札の即時ブロードキャストと「現在の同時接続人数」表示。
- **Phase 3 — 画面と LINE の連動**: 見ている人には画面で、離れている人には LINE で。終了間際の自動延長とも整合させる。

> 目標指標: 入札の画面反映 1秒未満／終了間際の負荷でも速報が落ちないこと。

## 総評

播州オクのフロントエンドは完成度が高く、**スマホの操作感ではすでにエドオクを上回る素地**がある。
認証・LINE通知・2重台帳といった「信頼の土台」も先行事例と同水準まで実装済み。
本PRで画像のEXIF/GPS無害化も完了した。

残る差は、バックエンドの**リアルタイム性（即時反映）**と、**信頼の可視化（QR・家系図）**に集約される。
次は P0「真のリアルタイム入札基盤」に着手すれば、先行事例を体感UXだけでなく機能面でも明確に超えられる。
